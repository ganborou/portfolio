# План реализации сайта-портфолио

Дата: 19 сентября 2026. План уточнён после исследования Figma MCP.

[Макет](https://www.figma.com/design/sEcSxhRnLbVaHHme9GwcoR/Portfolio?node-id=164-1127) · [Аудит, размеры, токены и node ID](design-audit.md)

## 1. Объём и архитектура

В макете есть главная, 6 категорий и 12 фреймов кейсов. Мобильный вариант найден для главной; адаптацию категорий и кейсов предстоит спроектировать. Три дополнительных desktop-фрейма показывают состояния интерфейса.

Стек: **React + TypeScript + Tailwind CSS**. Для сборки — Vite, для маршрутов — React Router. Контент хранить в типизированных локальных данных; CMS и бэкенд пока не требуются. Контактную форму макет не предусматривает.

Три шаблона страниц:

| Шаблон | Предлагаемый маршрут | Назначение |
| --- | --- | --- |
| `HomePage` | `/` | Hero, знакомство, направления, подход и контакты |
| `CategoryPage` | `/work/:category` | Две карточки проектов и описание направления |
| `ProjectPage` | `/projects/:slug` | Заголовок, роль/описание, год, внешняя ссылка при наличии, блоки кейса |

Категории: `websites`, `special-projects`, `product`, `posters`, `merch`, `animation`. URL — предложение реализации, а не свойства Figma. По карте макета получается 19 основных URL; в выпуск включать только готовые материалы. Отдельно предусмотреть 404.

Для кнопки «Назад» определить маршрут родителя: кейс → категория → главная. Это должно работать и при открытии прямой ссылки. При возврате из категории восстанавливать положение главной у списка направлений.

## 2. Этап 1 — завершить подготовку материалов

Исследование структуры, главной desktop/mobile, категории «Сайты» и состояний выполнено; подробности находятся в аудите. Перед реализацией каждого кейса получить его дизайн-контекст по дочерним секциям и уточнить состав экспортов.

- Получить web-файлы PP Mori Regular, Semibold и используемых курсивов; проверить кириллицу.
- Подготовить PDF резюме, реальные контакты, ссылки на внешние проекты.
- Исправить повторяющиеся описания в шапках кейсов мерча, продукта и анимации.
- Заполнить результаты продуктовых кейсов и материалы раздела анимации.
- Экспортировать портрет, знак, маски, обложки и первые материалы одного эталонного кейса; составить manifest `nodeId → путь → размеры → alt`.
- Уточнить поведение hero на touch и состояния направлений, которых нет в отдельных фреймах.

**Результат:** материалы для главной и одного полного пути «категория → кейс» готовы; для остальных кейсов есть список недостающего. Каркас можно делать параллельно с подготовкой контента.

## 3. Этап 2 — настроить проект

Git работает после установки Apple Command Line Tools; репозиторий распознан, `HEAD → main`. Коммитов и remote пока нет. Node.js и npm не найдены в PATH.

- Установить совместимую LTS-версию Node.js и проверить npm.
- Создать Vite-приложение на шаблоне `react-ts`, сохранив существующие документы. [Документация Vite](https://vite.dev/guide/).
- Подключить Tailwind через `@tailwindcss/vite` и импорт `tailwindcss`. [Инструкция Tailwind](https://tailwindcss.com/docs/installation/using-vite).
- Включить строгую проверку TypeScript, ESLint; сохранить lockfile.
- Настроить `dev`, `build`, `preview`, `lint`, `typecheck`, маршруты и 404.
- Выделить общие токены и компоненты; зафиксировать подготовленный проект первым коммитом после проверки.

**Готовность:** приложение запускается, прямые маршруты открываются локально, lint/typecheck/build проходят.

## 4. Этап 3 — визуальная система и главная

Общие компоненты: `PageContainer`, `ResumeLink`, `BackLink`, `SiteFooter`, `ProjectCard`, `CaseHeader`, `CaseMedia`.

Секции главной:

1. `HeroSection`: градиент и зернистость, роль и имя, опыт, специализация, резюме, скролл; `PortraitReveal` для состояния с фотографией.
2. `AboutSection`: крупный тезис, портрет с нужным смешиванием, биография и резюме.
3. `WorkNavigation`: шесть ссылок, квадратные маркеры, фоновые пятна и маски. Desktop — свободная композиция в ограниченной сцене; mobile — вертикальный список в порядке макета.
4. `ApproachSection`: тезис, пояснение, «Написать мне»; общий footer.

Токены: фон `#EFF2F1`, текст `#0F3142`, поля 32/16 px, заголовки 48/28 px, основной текст 24/18 px, названия направлений 28 px, footer 16 px. Полные параметры — в аудите.

Сначала собрать статические состояния на ширинах 1440 и 393 px, затем добавить взаимодействия. Не переносить всю страницу на абсолютные координаты из ответа MCP: основной контент строить Grid/Flex; локальные координаты допустимы внутри декоративной сцены направлений.

**Готовность:** главная соответствует двум эталонам, резюме и контакты работают, фон не вызывает переполнение, контент доступен с клавиатуры.

## 5. Этап 4 — категории и эталонный кейс

- Реализовать `CategoryPage` по разделу «Сайты»: на desktop две карточки с изображениями 443 × 528 и колонка описания, интервалы около 24 px.
- На узких экранах предложить порядок «заголовок и описание → карточки»; это адаптация реализации, поскольку отдельного макета нет.
- Создать модель `Category` с названием, описанием и списком проектов; `Project` со slug, category, title, year, summary, externalUrl и blocks.
- Для `blocks` использовать discriminated union: текст, изображение, группа изображений, видео. Добавлять разновидности только по реальному содержимому кейсов.
- Первым собрать кейс «Волна»: проверенная шапка, внешняя ссылка, последовательность медиа. Разобрать его по секциям через MCP, не запрашивать всю длинную страницу одним блоком.
- Заголовки и пояснения портфолио верстать текстом; демонстрационные мокапы и изображения интерфейсов хранить как медиа. Не реализовывать сайты клиентов внутри кейсов.

**Готовность:** полный сценарий главная → «Сайты» → «Волна» → назад работает на desktop/mobile; прямое открытие URL и обновление страницы проверены.

## 6. Этап 5 — остальные категории и кейсы

На общих шаблонах подключить остальные пять категорий и одиннадцать кейсов из таблицы аудита.

- Сайты и спецпроекты: длинные последовательности мокапов и презентационных блоков.
- Постеры: галереи с сохранением пропорций и достаточным размером изображения на мобильном.
- Мерч: изображения и анимация после уточнения описаний.
- Продукт: исследование, гипотезы, решения, результаты; заменить текстовые заглушки достоверными материалами.
- Анимация: получить видео, постеры и описания; не считать пустые фреймы завершёнными кейсами.

Экспортировать композиции отдельными блоками, а не одной картинкой высотой 15–17 тысяч пикселей. Подготовить несколько размеров изображений, явные размеры и lazy loading ниже первого экрана. Для видео — poster, controls, preload metadata; автоматическое воспроизведение только по обоснованному сценарию, без звука и с учётом reduced motion.

**Готовность:** для каждого публикуемого проекта есть финальное описание и медиа; отсутствуют заглушки и пустые ссылки. Готовность отмечать по каждому кейсу отдельно.

## 7. Этап 6 — взаимодействия, адаптив и доступность

- Реализовать состояния hero и направлений по отдельным фреймам; недостающие состояния согласовать как дополнения к макету.
- Для CSS-переходов использовать opacity/transform; отдельную библиотеку анимации добавлять только при необходимости. Длительности и easing макетом пока не подтверждены.
- Hover продублировать focus-состоянием; на touch переход по направлению не должен требовать скрытого hover. Слои Cursor не означают обязательную замену системного курсора.
- Поддержать `prefers-reduced-motion`, видимый фокус, достаточные зоны нажатия, alt-тексты, семантические заголовки.
- Проверить 393 и 1440 px как эталоны, дополнительно 320, 375, 768 и 1024 px. Breakpoints подобрать по реальному поведению контента.
- Проверить длинные заголовки и контакты, переносы кириллицы, масштабирование текста и контраст, особенно малоконтрастные ссылки «Скролл»/«Назад».

**Готовность:** все ссылки доступны мышью, клавиатурой и touch; нет переполнения и скачков макета при загрузке медиа.

## 8. Этап 7 — проверки и подготовка публикации

- Сравнить браузерные скриншоты с Figma на одинаковых viewport: главная в двух размерах, категория, шапка и медиаблоки кейса, hover-состояния.
- Выполнить lint, typecheck, production build.
- Добавить небольшое число E2E-проверок: путь до кейса и назад, прямой URL, 404, резюме и клавиатурная навигация. Unit-тесты нужны только для нетривиальной логики.
- Проверить загрузку длинных кейсов и отсутствие ошибок консоли/битых ресурсов.
- Настроить title/description, favicon, Open Graph, sitemap и canonical после определения домена. Если нужны отдельные социальные превью и индексируемый HTML каждого кейса, заложить пререндеринг маршрутов до выпуска.
- Подготовить конфигурацию хостинга: обработка прямых URL, кеширование, размещение тяжёлых видео. Затем выполнить согласованную публикацию.

**Готовность:** все проверки проходят, сборка воспроизводима, публикация содержит только готовый контент.

## 9. Структура файлов

```text
src/
  app/             # App, маршруты
  pages/           # HomePage, CategoryPage, ProjectPage, NotFoundPage
  components/      # ссылки, карточки, шапки, медиа и footer
  sections/home/   # hero, знакомство, направления, подход
  data/            # categories, projects, profile
  types/           # Category, Project, CaseBlock
  assets/          # шрифты, портрет, знак, маски
  styles/          # токены Tailwind, глобальные стили, эффекты
public/
  media/projects/  # материалы кейсов
  resume.pdf       # после получения файла
docs/              # аудит и план
```

Названия и структура — проектное решение; существующего кода для переиспользования пока нет.
